# R6 design: Hack-vN-AB quine with ROM and RAM built from gates

Status: design only, no R6 code or measurements yet. Figures marked [E] are estimates.

## Decisions (from Joshua, 2026-10-23)
- Layout: compact, but only to R4's level of compactness (no hard optimisation). Not loose dedicated lanes, because of the arm's 16-bit coordinate range.
- RAM: R1-style tiles (ram_word chain, 128 bytes), unchanged.

## Goal
Run with `--rom off --ram off`. The machine is the R1 Hack-vN-AB core (about 2208 core nodes plus the RAM tiles).
The program/description ROM becomes a plane of NANDs built from gates. The machine builds its own copy of that plane.

## Plan
1. Baseline: take R1's ROM image (builder code plus hd_data) and measure its cost as a ROM plane, using the E1 plane generator
   (about 2.2-2.3 NAND per stored one).
2. Compact placement: reuse R2c's compact layout approach (builder_c.asm and ram_c.asm in /home/claude/r2c/src) instead of R1's dedicated lanes.
   Check that the layout fits in the 16-bit arm range.
3. Builder change: after placing the core and tiles, emit the ROM plane. This means new builder code, and the ROM image must grow
   to describe the plane.
4. Self-reference: the plane's description has to be part of the ROM image the plane stores. Decide between a regular-pattern
   generator (cheap description) and an explicit list (large).
5. Verify with the same ladder as R5: rndp --build with 0 refused/faults, a pad-dump connectivity check, a model replay of the
   builder with a comparison of child against parent, and a gate-level run if feasible.

## Open risks
- Compact layout is the likely cost driver. R2c was about 2x the loose layouts; a ROM plane may widen that gap. [E]
- The 128-byte RAM limit may be too small for plane-emission code.
- R5 showed that layout-description density dominates cost. The plane description in the ROM image must stay regular.

## Next step
Measure R1's image as a ROM plane and read R2c's compact builder for what can be reused.

## Measurement 2 (2026-10-23): grid-structured plane netlist [M] (r6/grid_plane.py)
Structure chosen for physical layout: 128 x 128 cell grid. Row bus hi[h] and column bus lo[l] come from 7-bit predecoders; cell (h,l) is one
NAND of the two buses (shared by the bits of that byte); per row and bit an OR chain over the cells with a one; then a tree over rows.
R1 image: 57,107 NAND = 2.28 per one (the flat E1 plane was 51,643 = 2.06). Locality costs about +10 % (5.5k). Sampled-address check passes.
Per row and bit: mean 24.5 chained cells, max 104. Physical layout (strips per row, buses, router) is the next milestone; nothing placed yet.
Revised option B estimate: plane about 95-100k with the larger image, total about 110-115k [E].

## Physical plan for the plane (draft, 2026-10-23) [E]
Strip layout. Row h of the grid is a horizontal strip, 128 cell columns wide. The row bus hi[h] runs along the strip on layer 0. The 128 column
buses lo[l] run vertically through all strips on layer 1 (one track per column; strips are stacked in y). Cell (h,l) exists only if byte h*128+l is nonzero,
and sits at the crossing of its two buses. Per strip there are 8 bit lanes (one per output bit) running horizontally beside the cells. Chain gates for
bit j are placed in the cell's column, so a one costs: tap the cell output onto the lane j gate pair (NOT + NAND), one vertical hop.
Strip outputs (8 per strip) go to a reduction column at the strip end (tree over 128 rows, 8 bits).
Gate count 57k at 30-36 cells/gate (R2c 30, R3c 36 cells/gate measured) gives about 1.7-2.1 M cells, roughly 1,300-1,450 square. Fits in 16-bit arm range with the 4,700-class CHILD_DX of R1 shrunk accordingly.
Builder state needed per row: one byte per bit lane (column index of the lane's last chain gate) = 8 B. The 128 B RAM budget (R1 builder uses 118 B) is tight but workable.
Open issues:
1. Cell outputs fan out to up to 8 lanes (mean 3.4 ones per nonzero byte). Lane assignment and tap routing need a real router test (use r5 mrouter on a 16-row prototype).
2. RAM tiles: R1 stacks the 7,680 tile gates in one 23k-tall column (3 cells/gate pitch). A compact version should fold tiles into several columns; the tile data stays one stored 60-gate tile.
3. Decoder/predecoder (about 700 NAND for 14 bits) feeds 128 row buses and 128 column buses; place it on the strip edges.
4. Self-reference: the emitter code, tile layout and core layout are all ROM bytes, so the plane has to hold them. Fixed point on image size as in R5.
Prototype plan: (a) generate a 16-row x 16-column plane for a random ROM, place by the strip rule, route with mrouter, check pads vs netlist; (b) measure cells/gate;
(c) only then write the builder code (rom emitter) and a model that checks arm commands against the generator.

### Measurement 3d (2026-10-25): cpack placement (empty cells take no column) [M]
Each strip's nonzero bytes get consecutive 10-cell bands instead of fixed column slots; zero bytes take no space. 16 x 16, pitch 5: 216 x 765 = 165k cells
(149 per gate vs 170 for slot), router 0 failed nets and no overused cell, rndp connectivity checked as in 3b (see numbers below).
Lane sharing with fixed slots does not help: two bits in one lane need slots twice as wide, so the strip area is unchanged.
At 16 columns the gain is small because the widest row sets the width; the strip height (9 lane rows x 5 + 2 = 47) dominates. For 128 x 128 [E]:
width about 128 x 0.5 x 10 = 650 + edge, height 128 x 47 = 6,000, so about 4 M cells, roughly 70 cells/gate. Needs the 128-column test to confirm.
Builder cost: it keeps a running band index per strip (one byte), which is cheaper than the full column address.

## Important gap (2026-10-25): the prototypes use a router, the builder cannot
In proto_plane.py every wire comes from the PathFinder router. The builder is a Hack program with 128 B of RAM and no router, so every wire of the plane has to be a
fixed pattern computed from (strip h, band b, bit j). The placement is already formulaic (cpack: strip base y = 2 + 47h; band x = 8 + 10b; cell row y = base; lane j row
y = base + 5(1+j); chain NOT at (x, laneY), chain NAND at (x+5, laneY)), but the 35 k wires need a router-free scheme. Sketch (layer 0 horizontal, layer 1 vertical, as in R1):
- chain link inside a lane: horizontal on layer 0 along the lane row from the previous gate output to the next NOT input (no other lane's gate lies on that row);
- cell output w -> lane j gate: a vertical trunk on layer 1 in the cell's band (one column per bit j, 8 columns max, so the band must be wider than 10: needs about 5 + 8 = 13 cells) with a via and a layer-0 stub into the gate pin;
- hi[h]: horizontal layer 0 on the cell row from the strip edge to every cell's A pin (cell row has no other layer-0 wiring except the cell itself);
- lo[l]: the hard one. Cells of column l sit at different x in each strip (cpack). Either keep columns fixed (slot placement, 170 cells/gate) so lo[l] is a straight vertical on layer 1, or add a per-strip horizontal layer-0 jog row from the straight column to the band; the jog row costs 2 more rows per strip;
- strip results and the column reduction: a vertical layer 1 spine at the strip end.
Cost of this scheme is wider bands and extra rows, so expect the real cells/gate between the slot figure (140-170) and the cpack figure (70-100). The pattern must be checked with a generator + rndp connectivity test, like chk_proto.py but without the router. That is the next experiment; the router-based numbers above are a lower bound.

## Measurement 4 (2026-10-25): ROUTER-FREE plane generator [M] (r6/plane_gen.py, chk_gen.py, sim_gen.py)
Every wire is a fixed formula of (strip, column, bit); no router. Scheme: columns on a fixed pitch CW = 8 (so lo[l] is a straight layer-1 vertical at cx-1);
one strip per nonzero row (empty rows get no strip); cell NAND(hi[h], lo[l]) on the strip's top row; per output bit ONE OR-chain over the whole plane in (h,l) order
(first one: N = NAND(w,w); later ones: T = NOT(acc), N = NAND(T, w)); the chain returns from a strip's right end to the next strip's left end on a free row
(layer-1 verticals at x = XEND+2j and 2+2j). w reaches each lane gate through one layer-1 trunk at cx+3 with vias at the lane rows. There is no separate row/column
reduction (saves 3 gates per row-bit versus the grid netlist). Lane pitch LP = 5 rows.
Results on R1's real ROM image (16,288 B), all [M]:
| case | strips | NAND | board | cells/gate | track steps | vias |
|---|---|---|---|---|---|---|
| bytes 0-8191 (64 rows x 128) | 46 | 34,665 | 1,068 x 2,118 = 2.26 M | 65 | 1.37 M | 25,600 |
| full image (128 x 128) | 73 | 57,625 | 1,068 x 3,360 = 3.59 M | 62 | 2.16 M | 42,273 |
rndp loads both with 0 refused commands and 0 faults; every gate pin sits on its logical net (0 opens, 0 shorts, 0 undeclared pins; 172,875 pins in the full case);
the logical netlist reproduces the ROM byte for 650 sampled addresses per case (0 mismatches). This replaces the router-based estimates as the plane layout:
62 cells/gate is better than the router's cpack estimate because the strips skip empty rows and the chain removes the reduction column.
Gate count 57,625 NAND = 2.30 per one; the address predecoders (14 bits -> 128 hi + 128 lo lines, about 0.7 k NAND) and the hi/lo input stubs are NOT included yet.
Timing: RNDP settles the combinational network inside the tick (spec section 3), so the long chains (about 3 k ones per bit) cost no ticks, only simulator events.
Revised total [E]: R1 logic 15.3 k + plane 58 k + predecoders 0.7 k = about 74 k units before the emitter code and the layout/tile data go into the image.
Board about 3.6 M cells for the plane, plus the core and RAM tiles.
Still to do: builder code that emits this pattern (loops over strip/column/bit with the formulas in plane_gen.py), the predecoders, the interface to the CPU's ROM address and data
pins, and the 2,208-node core layout (option B stored layout) and tile column.

## Measurement 5 (2026-10-25): complete gate-level ROM with address decoders, all wires by formula [M] (r6/plane_gen2.py, sim_gen2.py)
Adds the address inputs a0..a13 (14 external nets), 14 inverters, and 73 hi lines + 128 lo lines. Each line is an AND of 7 literals built as a chain of 6 NAND + 6 NOT
(12 gates per line), taps from 28 vertical literal buses (layer 1) through vias and horizontal stubs (layer 0), one stub row per literal. The hi line output row is the hi trunk
row of its strip (lines exist only for the 73 nonempty rows); the lo block of 128 lines sits under the plane and each lo output runs along its own row to its column's layer-1 vertical.
Everything is a formula of (line, literal, strip, column, bit); no router. R1's real 16,288-byte image:
| LP (lane pitch) | NAND | of which decoders | board | cells/gate | track steps | vias |
|---|---|---|---|---|---|---|
| 5 | 60,051 | 2,426 | 1,184 x 4,910 = 5.8 M | 97 | 2.71 M | 43,822 |
| 4 | 60,051 | 2,426 | 1,184 x 4,326 = 5.1 M | 85 | (same wires) | 43,822 |
Checks: rndp loads each with 0 refused commands and 0 faults; all 180,153 gate pins sit on their logical nets (0 opens, 0 shorts, 0 undeclared); the netlist driven by the 14 address bits
reproduces the ROM byte for 700 sampled addresses (0 mismatches). Small cases (4x16, 16x32 rows x cols) checked for every address.
So a 16 KB ROM image costs 60,051 NAND = 2.39 NAND per stored one, all-gates and self-derivable [M]. The 2-stage group predecoder would cut the decoders from 2,426 to about 700 NAND
(about 1.7 k units, 3 %) and is left as an optimisation.
Revised R6 total [E]: R1 logic 15.3 k + ROM 60.1 k = about 75 k units, before the plane-emitter code (extra ROM ones) and the change from R1 loose lanes to the stored compact core layout.
Still open: (1) the interface (14 address nets from the core's addr.mux outputs into the a0..a13 inputs; 8 plane outputs into the core's rom0..rom7 sinks);
(2) the Hack builder code that emits all of this by loops; (3) the core layout (stored vs R1 computed lanes) and the RAM tile column; (4) the fixed-point on image size.

## Architecture of R6-B (decided 2026-10-25: option B)
Key simplification found in the layout tool (c3/layout/src/main.rs): ROM and RAM are *fixed parts with pin cells* at known positions, and the router ends paths on those pin cells.
So the stored compact core layout does NOT need the tiles or the ROM data in the netlist: R6-B = the existing R2c core (2,034 NAND + 56 DFF, `r2c_p5.lay`, already routed, with ROM and RAM as
placeholder parts) + three formula-built gate blocks reached through formula "interface wires" that start on the placeholder pin cells:
1. ROM plane (plane_gen2.py): 14 address inputs, 8 data outputs. Built [M].
2. RAM block, 128 x 8, address 7 + WE + DIN 8 -> DOUT 8: 128 select lines (my AND-chain line generator, 12 gates each, 8th literal WE for the write line) + 128 R1 tiles
   (60 gates: 52 NAND + 8 DFF; i0 = WE, i1 = tie-high, i2 = select line, i3..i10 = DIN broadcast, i11..i18 = previous tile chain; DOUT = output 8+c of the last tile).
   Tile layout: one stored 60-gate tile (about 0.4 KB) replicated, or a formula pattern. Not built yet.
3. Interface wires: 22 for the ROM (14 + 8), 17 + 8 for the RAM, from the pin cells on the core board's top/bottom margins to the blocks. Not built yet.
The builder does not place ROM or RAM parts; it runs the R2c builder for the core, then emits the blocks and the interface wires by loops. The ROM image = R2c image (13,050 B) +
emitter code (~2-3 KB) + the tile layout (~0.4 KB). The plane encodes that image; the child's plane is built by reading the parent's plane, so image equality is the quine condition.
Revised cost [E]: plane for ~16.5 KB (~51 k ones x 2.39) = ~122 k; core 2.4 k; RAM block (select lines 1.5 k + tiles 7.7 k NAND + 1,024 DFF x 6 = 6.1 k) = ~15.3 k; total ~ 140 k units.
Test-speed risk: rndp re-settles the plane cone (thousands of events) on every ROM address change, so a tick-level run of the whole quine (R2c needed 15 M+ ticks) may be very slow; the event limit
(--event-limit, default 5 M per phase) is fine. Plan: verify the child by builder-model equivalence plus rndp connectivity, and run a shortened tick-level test of the plane + CPU.
Work packages: A RAM block generator and checks; B interface wires and board assembly; C builder code (Hack) and its model vs generator; D image fixed point; E verification.

## Measurement 7 (2026-10-25): RAM block from gates, 128 x 8 [M] (r6/tile_gen.py, ramblock_gen.py, blk.py, ram_sim.py)
Tile = R1's word tile with the two redundant select gates folded away: inputs WE, SEL, DIN0-7, chain-in 0-7; 58 gates (8 DFF + 50 NAND); routed ONCE with the R5 mrouter
(50 x 56 cells, 0 failed nets, 316 tracks, 27 vias) and replicated by translation; stored size of one tile is about 300 tracks/gates (~0.4 KB of layout data, to be counted in the image).
Block = 128 select lines (7-literal AND chains, the same formula as the ROM decoder, aligned to each tile's SEL port row) + 128 tiles + WE/DIN bus verticals + chain links
+ tie-high NAND for the first tile + 8 output inverters (DOUT active high).
Result: 7,952 NAND + 1,024 DFF = 8,976 gates, board 163 x 7,310 = 1.19 M cells (133 per gate; the tile column is long and narrow), 518 k track steps, 8,839 vias.
Checks: rndp loads it with 0 refused and 0 faults; all 25,904 gate pins on their logical nets (0 opens, 0 shorts, 0 undeclared); cycle simulation of the logical netlist,
1,500 random write/read steps against a Python model, 0 mismatches (read sees the pre-write value, as in RNDP).
Cost: 7,952 + 6 x 1,024 = 14,096 units for 1,024 bits (13.8 units per bit). The select lines are 128 x 12 = 1,536 of the NAND; a 2-stage predecoder would cut that to about 400.
Note for the port pads: a router-made tile's copper may leave a port pad on either layer, so every port cell gets a via when blocks are joined.
Next: WP-B, the interface wires and board assembly: the core (r2c_p5.lay) with the ROM plane and this RAM block attached at the ROM/RAM pin cells.

## Measurement 8 (2026-10-25): core + ROM plane + RAM block assembled and checked [M] (r6/assemble.py, chk_full.py, layout_vp.patch, r2c_vp_p5.lay, plane3_gen.py)
**Pins on the board edge.** The R2c core's ROM/RAM pin cells were walled in by routing (a net-by-net escape router found 20 of 39 nets unroutable), so the layout tool got a `vp=S` option
(patch in layout_vp.patch): ROM and RAM pins become virtual pins spaced S=3 cells apart in the top row (ROM: 14 address + 8 data) and the bottom row (RAM: 7 address, WE, 8 DIN, 8 DOUT) of the
core board, and the parts are not placed. Re-annealing and routing R2c at pitch 5 (same netlist) succeeded for 7 of 8 seeds in 25 s each; the best (seed 1) has 9,680 track segments and 1,267 vias
(original r2c_p5: 9,867 and 2,120) and its stored path data is 10,188 B (total ROM image 12,716 B instead of 13,050 B with the unchanged R2c builder).
**Interface wires are pure formula**: from pin m (x = 4 + 3m) one vertical on layer 1 into a corridor row (-2-m above the core for the ROM, row 276+k below for the RAM), a horizontal on layer 0 to the target
column, a vertical to the block's input. Plane data outputs run on rails right of the plane. 324 commands for all 46 wires (22 ROM + 24 RAM), no stored data. Every pin cell needs a via (path copper starts on one layer).
**Whole board** (core 2,090 gates + plane 93,949 + RAM block 8,976 = 105,015 gates, 635 k commands in the plane3 variant): rndp loads with 0 refused/0 faults; 313,978 gate/arm pins all on the expected nets, 0 opens, 0 shorts.
**Tick-level run** (the old R2c builder program reading its ROM image from the *plane*, its variables in the RAM *block*, the unchanged CPU; 300 k ticks): all 909 arm commands identical to the reference R2c board with ROM and RAM parts
(same ticks, same arguments), 0 mismatches. Cost of the plane in the simulator: 23.4 G settle events in 550 s (42 M/s) = 78 k events per tick against 0.9 k for the reference, so a full 25 M-tick quine run would take about 13 h of simulator time.
(The "would join two drivers" faults in that run are the old builder placing its child on top of our plane; expected.)
**ROM budget (new finding): the Hack-AB CPU maps ROM data at 16384..32767, so the image is capped at 16 KiB.** R2c's builder code is 2,178 B (1,089 instructions of 2 bytes); with the vp layout the data is 10,188 B.
Headroom for the new emitters + tile data: 16,384 - 12,716 = 3.7 KB (plus about 0.2 KB freed by dropping the ROM-programming and RAM/ROM place code). This is the binding constraint for WP-C: emitters must be table-driven.
**plane3 (uniform, state-free plane)** for emitter economy: all 128 strips exist; every lane is one snake wire (pass slot or gadget slot per ROM bit, then a fixed return path at the strip end, next strip's lane row below);
the chain starts on a floating net (reads 0 in rndp, as the tie-high gate of the RAM block already relies on). No per-lane state, no data-dependent lengths, hi trunk/lo verticals/buses uniform.
Cost: 94,269 gates (+320 for the 26 empty rows' hi lines), board 1,184 x 7,825. Checks: logic simulation vs ROM bytes (700 addresses) 0 mismatches; rndp 282,807 pins 0 opens/0 shorts; whole board
(core + plane3 + RAM) 314,938 pins 0 opens/0 shorts. Emitted per ROM byte: cell (if nonzero) + 8 slots (gadget 9 commands or pass 1 command).
Next: WP-C, the Hack emitter: a template/item interpreter (origin + signed 8-bit offsets) for cell, gadget, inverter, RAM tile; inline code for the decoder line, snake connectors, interface wires.
