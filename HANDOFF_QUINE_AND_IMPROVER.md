## 2. The world and the two machines in brief

* **RNDW v0.5** (`nandgen/RNDW_SPEC.md`): parts are NAND, DFF, ROM, ARM (robot arm), wires. The arm is a memory-mapped write-only device (registers 0–15, CMD in 15: 1 PLACE, 2 WIRE, 3 PROGRAM_ROM); coordinates are signed 16-bit offsets from the issuing arm. A ROM can be programmed only before any wire touches it; `run` is wired last and feeds exactly one gate. Faults are counted, never visible to circuits; tests assert zero.
* **Hack-vN / Hack-vN-AB**: Hack derived von Neumann ISA, 8-bit data, 16-bit instructions fetched as two bytes, one new instruction AP (indirect pointer load), memory-mapped arm. X uses AB = 13, Y uses AB = 15 (the maximum for the 15-bit A-instruction; AB = 16 would be a different ISA, and the agreed fallback if more is needed is to stop and discuss RV32EC).
* **X**: the description (CPU netlist) is a stream of Exp-Golomb back references; the RAM is generated by loops (one 60-node word tile replayed per word); the builder is a tile engine that walks the node list twice (place, wire).
* **Y**: seed g1 is the textbook (level 0) core plus a 256-word RAM tile chain; the HD has library modules (not, and, or, xor, mux, ha, fa, RAM word tile) and a body that instantiates them. The builder walks the body once per module type (16 groups) in two phases; before each group `improve_type` runs the improver on that type's record. The improver (stable compaction, cuts of ≤ 3 leaves, truth tables, exhaustive iterative-deepening NAND search up to 6 gates, rewrite, partition, layout in slot form) writes an improved record into a 40 B RAM buffer which the builder reads exactly like a ROM record and also programs into the child's ROM.

## 4. How to run (from `nandgen/y`; build the simulator first with `cargo build --release --offline` in `nandgen/rndw`; no absolute paths needed since 2026-10-15, `$RNDW` overrides the simulator location). Minimal file set for `run_y_world.py`: see M7_WRITEUP §9 (includes `isa/fastsim.py`, which `machine_lockstep.py` imports)

```
python3 tests/test_m5.py && python3 tests/test_m5_improver.py     # builder and improver in the assembly model
python3 tests/test_m6_audit.py && python3 tests/test_m6_behaviour.py
python3 tools/trace_check.py ...                                   # listing coverage (see test_m2/test_m5 for the invocation)
python3 tests/run_y_world.py HDFILE STEPS [OUTDIR]                 # RNDW run; builds the seed and improved images
python3 tests/verify_y_world.py STATE G:HDFILE:IMAGE ...           # check a saved world against the reference
(cd isa && HACK_AB=15 python3 coretest.py 10 20)                   # core decode + kernels at AB = 15, ~20 s
```
A saved state resumes with `rndw --world FILE --steps N --save OUT`; the `cfg` line holds the grid and ROM address bits. Resuming restores the DFF values (checked: improver g2 + 90 M ticks built g3, identical to the reference). `--svg-at-end --svg-window X0,Y0,X1,Y1 --svg-scale S --out-dir DIR` draws a window; wide windows are uninformative (wires drawn as fans), use small ones.

## 5. Decisions made (by Joshua)

* X: find the minimum RAM by measuring the program's high-water mark; ROM may grow beyond 4 KiB (report it as part of X); arm-relative coordinates (spec v0.5) so the child's ROM is byte-identical to the parent's.
* Y: M3 review: increase ROM and address size as needed (→ AB = 15); M4: accept the tighter RAM and see what the improver needs; M6 review: **accept RAM 256 B** ("seriously impressed at what you managed to fit in there"), leave the improver's persistent state as is, keep power-of-two RAM.
* Standing requirements: every ROM byte explainable (commented listing, `trace_check`); Python experiment first, then ROM; no cargo dependencies without asking; push back on mistakes; report caveats and label estimates.

## 6. Things to be careful about

1. **The ROM is full.** 16,350 of 16,384 bytes at AB = 15. Any more code or description needs a different ISA or a smaller builder/improver.
2. **Signed 8-bit jump tests.** A subtraction followed by JLT/JGE is wrong for values ≥ 128 (the RAM tile index runs to 255 at W = 256). This caused the main M5 bug; the builder splits such comparisons (`ti_d64`) or tests equality.
3. **No stack.** Calls use `CALL`/`RET` macros with a fixed return slot per routine (`RA_*` in `ram.asm`), so no recursion; routines that never call anything share one slot.
4. **RAM overlay.** Builder and improver temporaries share addresses 0–127 on purpose; only the 29 B persistent block (168–196) and the 40 B record buffer RECB (128–167) cross calls. Changing a variable's address means re-checking `ram.asm` for overlaps; the high-water mark is measured with RAM pre-filled with 1s (as built RAM powers up).
5. **Record format is fixed-extent.** An improved record must fit the old record's space (slot form with holes, REC_MAX 40 B); `hd2asm.py` asserts the PICKHI divisor ≤ 64 and pads the module area (`MOD_AREA` 0x1C0).
6. **Only combinational library modules are improved.** The DFFs, the RAM array (2,048 of the 2,104 DFF), the arm, the ROM size and the improver itself are never changed. "Improves its gate-level logic" is the claim; "improves itself" is not.
7. **The seed is textbook.** The improver removes redundancy that the seed contains. A seed that is already optimal improves nothing, and the 946 NAND are in some sense a property of the seed choice. Audit B shows the improved gate lists are not stored in ROM; audit C shows xnor, maj and and3 are handled without being in the seed library.
8. **Cost model.** Weighted cost NAND + 6·DFF gives −3.4 %. If ROM bits are charged at the earlier factor (f × 12.3 per bit) the improver's ~8 KB of code costs more than it saves for any f ≳ 0.01 (estimate). Decide which figure is the headline before quoting Y.
9. **Checkpoints.** `run_y_world.py` saves a checkpoint every `$CHUNK` ticks (default 10 M) and `RESUME=1` continues an interrupted run (added 2026-10-15; the M6 runs predate it, and one was lost to a session restart). **Time estimates.** Y's tick figures are derived, not measured. Wall-clock for a 200 M tick run was about 7 h on the shared 2 cores; the session can be restarted mid-run (one run was lost that way; use `--save` and resume).
10. **Workspace vs Project.** The cloud workspace is not persistent across sessions; the Project is. `project_write` needs absolute local paths. Y_SPEC lives at `nandgen/Y_SPEC.md` (not `nandgen/y/`). The Project knowledge budget is 2,000,000 B (about 0.64 MB used before M7 uploads).
11. **Mutation testing caveats.** 60/60 killed in M6 is a sample of executed words, with an oracle slightly stricter than set equality; dead code cannot be tested that way. The core-decode mutation sample (M1, AB = 14) killed 59 of 60 (the survivor differs only in non-one-hot states).
12. **Documentation drift.** `Y_SPEC.md` still contains the AB = 14 plan in several places (sizes, expected ROM); `HACK_VN.md` is X's (AB = 13) and `HACK_VN_AB.md` is Y's. `y/isa/` is Y's own copy of the ISA files and differs from `nandgen/isa/`.

## 7. Open questions and suggested next steps

* **Make the improver improvable.** Put the improver's own gates, or a better improver, into the loop; the fixed point would then be about more than the library. Needs ISA/ROM headroom (see 6.1) and a way to charge for the improver's cost.
* **Decide the cost model** (6.8) and maybe re-report X and Y with ROM bits included.
* **Measure ticks per generation** for Y (a counter in the model, or a shorter RNDW run with markers).
* **A non-textbook seed**, or deliberately partly optimised, to see where the improver stops paying; larger search depth (GMAX > 6) is possible in principle but costs RAM and time.
* **Smaller X and Y.** X's open items: RAM 16 B would need the variables down from 30 B; a smaller core netlist (run the nandgen optimizer) is the larger lever (BUILDER_NOTES "Where the bytes are"). For Y the builder is generic reference machinery (`add16`, `rdb`, `emit`, `gates`, `put5` dominate time) and could be tightened.
* **The research question itself.** X and Y are upper bounds from real designs (HANDOFF §5): code showing X bytes suffice never shows X are required. Lower bounds need counting arguments; the tau_r / tau_i / tau_c framework (Kabamba, Owens and Ulsoy) and the "where is the design hiding" list in HANDOFF.md still apply: hand-optimised cells, the HD format and tools, DFF/arm as primitives, the ISA, the test bench as specification.
