# Hack-vN-AB: the Hack-derived von Neumann ISA as used by data point Y

Status: M1 deferred this merge to M7 ("merge into a HACK_VN_AB.md"); it was missed in the first M7 delivery and added afterwards. It is a delta document on top of `nandgen/isa/HACK_VN.md` (X's ISA, AB = 13): everything not mentioned here is as in that document. Y uses **AB = 15**. Sources of truth: `isa/common.py`, `isa/isahack.py`, `isa/nl_hackvn.py`, `isa/nl_core.py`, `M1_REPORT.md`, `src/macros.asm`.

## 1. What AB means

AB is the width in bits of the address bus, of PC, of A and of the AP pointer. Data stays 8 bits wide, the ALU stays 8 bits, instructions stay 16 bits fetched as two bytes (low byte first). X is AB = 13; Y chose AB = 15, the maximum, because the A-instruction has only 15 value bits (`0 vvvvvvvvvvvvvvv`). AB = 16 would need a new instruction format, i.e. a different ISA. (M1 originally expected AB = 14; the ROM outgrew 8 KiB, and at the M3 review you approved increasing ROM and address size as needed.) Everything below is for AB = 15 and gives AB-general formulas in brackets.

## 2. Memory map (AB = 15, 256 B RAM)

| addresses | size | what | notes |
|---|---|---|---|
| 0x0000–0x00FF | 256 B | RAM | selected when address bits [AB-1 : ram_abits] are all 0 (`ram_abits` = 8). It is *not* mirrored. |
| 0x0100–0x3FEF | | unmapped | reads return 0, writes are ignored |
| 0x3FF0–0x3FFF | 16 B | ARM registers [ROM_BASE−16 …] | write-only window; reads return 0. Decoded as addr[AB−1] = 0 and addr[AB−2 : 4] all ones. Register r = A[3:0]. |
| 0x4000–0x7FFF | 16 KiB | ROM [ROM_BASE = 2^(AB−1)] | selected by addr[AB−1]; writes ignored. Reset PC = 0x4000. ROM address on the part = A − 0x4000 (`rom_abits` = AB−1 = 14). |

Y's image is 16,350 B of the 16,384 B (34 B free). RAM size is a world constant chosen per machine (`ram_abits`), independent of AB; the RAM itself is generated by the builder (it is not part of the core netlist). AB = 13 gives X's map (RAM below 0x0FF0, ARM 0x0FF0, ROM 0x1000); AB = 14 gives ARM 0x1FF0, ROM 0x2000.

## 3. Registers and instructions (what changes with AB)

* **Registers:** D 8 bits; A, PC AB bits; IR-low 8 bits; IR-high keeps only the 5 bits that C-instructions use; 5 one-hot state bits. Bare CPU DFFs: 2·AB + 8 + 8 + 5 + 5 = 56 at AB = 15.
* **A-instruction** `0 vvvvvvvvvvvvvvv`: A = v[AB−1:0]. All 15 bits are used at AB = 15, so any address in the 32 KiB space can be formed by one instruction (this is why `@label` works for every ROM address with no paging).
* **C-instruction** `111 a cccccc ddd jjj`: unchanged (18 comp codes, dest A/D/M, 7 jump conditions). **Dest A writes A[7:0] only; A[AB−1:8] is left unchanged** — this matters for code that computes addresses (use the AP instruction or an A-instruction for the high part).
* **AP** `110 xxxxxxxxxxxxx` (the one addition to Hack): A = { mem[A+1][AB−9:0], mem[A] }. At AB = 15 that is a 15-bit pointer stored in two bytes (little endian), the high byte contributing its low 6 bits (`mem[A+1][5:0]`, AB−9 = 6). Two data reads. Y uses it for every ROM pointer and for all indirection (`@ptr ; AP ; D=M`).
* **Jumps:** target is A as it was before the instruction; the test is on the **signed 8-bit** ALU output. Consequence found in M5 (a real bug): comparing a quantity that can reach ≥ 128 (the RAM tile index runs to 255 at W = 256) with a subtraction followed by JLT/JGE gives the wrong answer. Y's code splits such comparisons (`ti_d64` etc.) or tests equality/zero.
* **No** carry flag, no shifts (use D+D, D+M), no stack, no call/return. Y emulates subroutines with a macro pair `CALL`/`RET` that stores a return address in a fixed RAM slot (`RA_<name>`, 2 bytes), so calls cannot nest recursively; the improver's leaf routines share one slot, as do the routines called from `improve_type` (`src/ram.asm`).
* **Halt** (model and builder): a jump to the A-instruction immediately before it.

## 4. Timing and gate level

One memory address per tick; read data is combinational, writes are clocked in the same tick. States: F0 (fetch low byte), F1 (fetch high byte; A-instructions finish here), X (execute C-instruction), AP0, AP1 (the two pointer reads). A-instruction 2 ticks, C-instruction 3, AP 4 — identical to X, so the ISA's tick and access counts do not change with AB (checked: K1–K4 give the same counts at AB = 13/14/15). The builder's demo and the estimate used in M6 (≈ 2.6 ticks per executed instruction, demo of 131 instructions in 336 ticks) rest on this.

Size, measured with nandgen:

| | AB=13 | AB=14 | AB=15 |
|---|---|---|---|
| bare CPU, level 2 (hand-optimised cells) | 705 NAND + 52 DFF | 730 + 54 | 755 + 56 |
| core (CPU + decode + read mux), level 2, `ram_abits` 8 | | | 823 NAND + 56 DFF |
| core, level 0 (textbook, the Y seed's core) | 1,886 (`ram_abits` 5) | 1,958 (`ram_abits` 5) | 2,021 NAND + 56 DFF (`ram_abits` 8, remeasured for this document) |

Each extra address bit costs about 25 NAND and 2 DFF. The core's interface is `romdata[8]`, `ramrd[8]`, `run` in; `rom_addr[14]`, `arm_addr[4]`, `arm_en`, `wdata[8]`, `ram_addr[8]`, `ram_we` out; `run` feeds exactly one gate (the reset), so it can be wired last.

## 5. The arm as seen from the CPU

Writes to 0x3FF0 + r set arm register r; a write to r = 15 triggers the command (spec v0.5, coordinates are signed 16-bit offsets from the arm that issues them):

| reg | meaning | reg | meaning |
|---|---|---|---|
| 0,1 / 2,3 | A.x / A.y (lo, hi) | 8 | KIND (0 NAND, 1 DFF, 2 ROM, 3 ARM) |
| 4,5 / 6,7 | B.x / B.y (lo, hi); B.x is also the ROM address | 9 | ANGLE |
| 10 | VAL (ROM byte) | 15 | CMD: 1 PLACE, 2 WIRE, 3 PROGRAM_ROM |

Registers persist between commands, so the builder only rewrites what changed. The builder uses 16 B of address space for this and nothing else outside RAM and ROM.

## 6. Idioms used by Y (all 2-byte instructions)

| operation | code |
|---|---|
| D = M[var] / M[var] = D | `@var ; D=M` / `@var ; M=D` (macros `LD`, `ST`) |
| constant 0..255 to a variable | `@k ; D=A ; @var ; M=D` (macro `SET`) |
| 16-bit constant to a variable | `@lo(k) ; D=A ; @v ; M=D ; @hi(k) ; D=A ; @v+1 ; M=D` (`SET16`) |
| read ROM or RAM through a pointer | `@ptr ; AP ; D=M` (`rdb`, `irdb`) |
| 16-bit add with carry | no carry flag: add the low bytes, detect the carry by comparing the old and new low byte signs (`add16`) |
| conditional jump | `@label ; D;JNE` etc. (test on the signed 8-bit result) |
| arm command | `@0x3FF0+r ; M=D` for each register that changed, then the CMD write |

## 7. Verification (from M1, still valid; Y's code additionally runs in the lockstep harness)

* `test_hackvn.py`: K1–K4 lockstep against the behavioural model at AB = 13/14/15 (AB = 15: K1–K4 and fuzz).
* `fuzz_hack.py`: random 800-instruction images covering all comp codes, destinations, jumps and AP (AB = 13: 22,921 and AB = 14: 22,935 instructions compared, 0 mismatches; AB = 15: 7,654).
* `coretest.py`: the core with decode and an external RAM in lockstep; exhaustive check of every address in four CPU states with random other registers (AB = 14: 65,536 checks). **Rerun at AB = 15 on 2026-10-14: exhaustive decode check 131,072 addresses ok (with `ram_abits` 8 and 10), boundary program 226 instructions, K1–K4 (same tick counts as at AB = 13: 25,572 / 28,156 / 7,618 / 86,905), 20 fuzz images, 73,443 instructions compared, all ok.** (With `ram_abits` 8 the K2/K3 test layouts use RAM addresses ≥ 256 and fail by construction, so the kernel part was run at `ram_abits` 10; the decode check does not depend on it.)
* RNDW simulator vs nandgen.Sim: 4,000 random-input ticks at AB = 14 (`xcheck_y.py`); Y's AB = 15 machine is exercised by the full RNDW runs (M6) and by the behaviour test (30 random programs in lockstep, 30/30, on the improved 256 B machine).
* Mutation of the core decode (AB = 14): 59 of 60 killed; the survivor differs only in non-one-hot states.

## 8. Known weaknesses (as in X, plus)

* Code density: every memory operation is `@addr ; X=M` (4 B); Y's builder + improver are 12,928 B of code for that reason.
* Signed 8-bit tests (§3) are an easy bug source; M5 found one.
* AB = 15 is a hard ceiling for this ISA, and the Y ROM is 34 B from full. Going further means a new instruction format (RV32EC was the agreed fallback).
